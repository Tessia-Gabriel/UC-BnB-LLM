# 新手读懂这个项目：LLM4Branch、我们的目标与眼前的问题

更新于 2026-09-14，对应项目完成 Phase 2 短预算实验后的状态。

这份文档不要求你先学过电力系统、数学优化或大语言模型。
你可以先读第 1、4、6、9 节，再按需要补充其他部分。

文中关于 LLM4Branch 的说明依据本仓库锁定的上游代码和 README，
不是对其全部论文实验的独立复现。我们自己的结果只适用于已执行的实验。

## 1. 先用三句话说清楚

**UC 要解决的是：为了满足用电需求，哪些发电机什么时候开、什么时候关、发多少电，才能省钱。**

**LLM4Branch 要解决的是：让大语言模型提前帮我们写“小规则”，让负责算答案的软件更快找到并确认最好的答案。**

**我们想进一步研究：如果这些小规则懂得发电机之间、前后时段之间的联系，能不能比只盯着一个开关更有效？**

目前已经做到“软件能运行，新的问法不会故意漏掉正确答案”，
还没有做到“新方法稳定比原来的软件更好”。

这不是同一件事。计算器能正确算数，不代表它比另一台计算器算得快。

## 2. UC 到底是什么？为什么不直接用最便宜的发电机？

UC 是 Unit Commitment 的缩写，中文通常叫“机组组合”。
“机组”可以先理解成一台发电机，“组合”就是安排哪些机器一起工作。

假设有两台机器：

- A：运行时比较便宜，但启动一次很贵，启动后需要连续运行一段时间。
- B：运行时比较贵，但开关比较灵活。

某几个时段的用电需求先低、再高、再低。你不能只看眼前这个时段：

- 现在不开 A，下一时段可能来不及满足高需求。
- 现在开 A，后面需求下降时，它可能还不能马上关。
- 频繁开关机器，启动费用可能超过节省的运行费用。
- 机器从小出力变成大出力也需要过程，不能总是瞬间变化。

所以我们要安排的是一整段时间的计划，而不是每个时段独立挑最便宜的机器。

当前模型主要检查这些事情：

| 日常说法 | 文档中的叫法 |
|---|---|
| 发出的电要满足需求 | 功率平衡 |
| 每台机器有最小、最大发电能力 | 出力上下界 |
| 相邻时段不能随意大幅增加或减少出力 | 爬坡限制 |
| 开机后必须保持一段时间 | 最小开机时间 |
| 关机后必须等待一段时间才能再开 | 最小停机时间 |
| 发电、保持开机和启动都要花钱 | 目标函数中的成本 |

我们现在使用的是简化练习环境：需求事先已知，不模拟输电网络、储能等复杂情况。
它适合先验证方法，不能直接等同于真实电网调度系统。

### 一个特别容易混淆的问题

这里有两种完全不同的“省”：

1. **发电计划省钱**：找到运行成本最低的合法计划。
2. **计算过程省时间**：让电脑更快找到并确认这个计划。

我们的研究主要改进第二种。理想情况下，不同正确方法最后得到相同的最低成本，
只是计算时间不同。不能因为某种方法得到“更低的数字”就认定它更好，
还必须确认它没有违反供电或设备限制。

## 3. 电脑如何找答案？“分支”又是什么？

项目里负责真正求解的软件叫 SCIP。你可以把它看成一位非常有经验的解题员。

### 3.1 为什么不能把所有计划试一遍？

一台机器在一个时段有开、关两种选择。10 台机器、8 个时段，
光开关位置就有 80 个。如果不考虑限制，组合数是 2 的 80 次方。
真实约束会排除很多组合，但逐个列举通常仍不现实。

SCIP 会利用问题中的数学关系，成批排除不值得继续尝试的方案。

### 3.2 先算一道“放宽要求的题”

现实中的开关只能是关或开，也就是 0 或 1。
为了得到有用的提示，电脑可以暂时允许开关取 0.4、0.7 这样的值。

这不是说机器真的能“开机 40%”。它只是临时放宽了开关限制，
用来计算一个乐观估计。机器开着但只发部分功率，则是另一个不同的决定。

技术文档把这种放宽后的计算叫“LP 松弛”。你只需要记住：

> 它不是最终发电计划，而是帮助判断哪些方向值得探索的一道简化题。

### 3.3 再把问题拆成两道题

如果简化题让 A 在第 3 时段的开关取 0.4，可以拆成：

```text
当前尚未解决的问题
├─ 分支一：A 在第 3 时段必须关
└─ 分支二：A 在第 3 时段必须开
```

两边都被保留，不是猜一边然后丢掉另一边。
再结合供电、成本等信息，有些分支很快就能被排除，另一些需要继续拆。

这个过程会形成一棵搜索树。树上的“节点”是一道尚待处理的子问题，
不是发电机，也不是大语言模型的 token。

实际 SCIP 还会使用其他数学技巧；这里仅用最简单的拆题过程帮助理解。

### 3.4 为什么“先问哪个问题”很重要？

就像排查故障：有的问题一问就能排除一大批可能性，有的问题问完几乎没帮助。

分支规则就是帮助 SCIP 决定：**现在先用哪一个条件拆题？**
好规则可能让它少走很多弯路。但规则本身如果计算得很慢，也可能得不偿失。

### 3.5 “找到了答案”和“证明答案最好”不一样

假设已经找到一个合法发电计划，费用是 110 元；数学推理说明最低费用不可能低于 100 元。

这时我们知道最好答案在 100 到 110 元之间，但还不能确定 110 元就是最好。
技术文档中的“gap”，可以粗略理解为这种尚未消除的不确定范围；具体百分比有计算口径。

- “找到可行解”：已经有一个合法计划。
- “证明最优”：已经确认没有更便宜的合法计划，在求解器数值容差范围内成立。
- “超时”：时间到了；可能已有不错的计划，但还没有完成证明。

所以“30 次都找到了计划”和“30 次都解至最优”不能混用。

## 4. LLM4Branch 做了什么？

LLM 就是大语言模型。这里主要借助它读说明、写代码、修改代码的能力。

LLM4Branch 没有要求它直接写出一个电力调度答案。原框架处理的是更一般的优化问题，
让 LLM 编写的是：**给候选分支变量打分的一小段程序。**

### 4.1 它的工作循环

```text
给 LLM 一份编程任务和已有程序
    ↓
LLM 提出一个评分程序
    ↓
在真实求解器上运行它，测量节点数、时间等结果
    ↓
调整程序中的数字参数，保存程序与成绩
    ↓
把较好的程序作为后续修改的参考，继续尝试
```

LLM 说“这个程序很好”不算数。必须让求解器实际跑，成绩才算数。

可以把它想成“设计比赛策略”的过程：LLM 负责提出策略，真实比赛负责检验。
它生成的代码不一定合法，不一定正确，更不一定快，因此需要检查和筛选。

### 4.2 评分程序输入和输出什么？

输入是求解器当前可供选择的变量，以及描述这些变量的一组数字。
这些数字叫“特征”，可以理解为每个候选的情况介绍。

例如：这个开关目前离 0 或 1 有多远？过去在类似方向上拆题的效果如何？
评分程序给每个候选一个分数，求解器选分数最高的变量进行分支。

我们复用的版本提供 91 维通用特征。新手现在不需要记住这 91 项，
只需要知道：它们是算法读取的数值信息，不是 91 条自然语言提问。

### 4.3 “调参数”不等于“训练大模型”

假设规则是“因素 A 乘 0.5，加因素 B 乘 0.5”。
调整这两个 0.5，是调整小程序的参数。

改变大语言模型内部的权重，让它以后更擅长写程序，才是另一层意义上的模型训练。
这两件事不能因为都叫“优化”就混在一起。

LLM4Branch 使用参数优化工具帮助寻找小程序里的数字；
程序的写法、结构则由 LLM 提出或修改。我们的复现目前只证明这条调用链跑通。

### 4.4 最终求解时还要不停问 LLM 吗？

我们的目标是不需要。

研究阶段可以花时间让 LLM 设计、试验规则。真正使用时，只运行选定的小程序，
不必在每个搜索节点调用大模型。

可以类比：教练可以花很久设计战术，但运动员比赛时不能每跑一步就等教练重新写一篇分析。

### 4.5 几个软件分别做什么？

| 名字 | 在本项目中的角色 |
|---|---|
| SCIP | 实际解题，维护搜索过程和正确性检查机制 |
| Ecole | 帮我们的程序读取求解状态和候选信息；Phase 0 也通过它执行变量选择 |
| OpenEvolve | 管理不断生成、评估、保存、再修改程序的循环 |
| LLM4Branch | 把 LLM 写规则、调小程序参数、求解器反馈连成一套方法 |
| 我们自己的代码 | 建立 UC 题目，定义新的分支问题，把它们交给 SCIP，并做实验 |

我们不重新造一整套程序搜索框架，而是在现有框架上研究新的分支方式。

## 5. 我们与 LLM4Branch 的区别是什么？

LLM4Branch 的核心问法是：

> 在已有候选变量中，现在最应该先处理哪一个？

例如：“先问 A 第 3 时段开不开，还是先问 B 第 5 时段开不开？”

我们想扩大可以问的问题：

> 除了一个开关，能不能先问一组有关联的开关？什么情况下这样问更有用？

原因是 UC 有很强的联系：一台机器前后时段的决定互相影响，同一时段不同机器又要一起满足需求。
但“有联系”只是研究动机，**还不是这种分支一定更快的证明**。

### 5.1 四种已经实现的问法

| 代码名字 | 白话意思 | 示例 |
|---|---|---|
| VAR | 问一个开关 | A 第 3 时段开还是关？ |
| UNIT_ON_COUNT | 问一台机器在一段时间内开着几个时段 | A 在第 1–4 时段共开着不超过 2 个，还是至少 3 个时段？ |
| START_COUNT | 问一段时间内启动了几次 | A 在这个窗口启动不超过 1 次，还是至少 2 次？ |
| GROUP_ON_COUNT | 问同一时刻一组机器开着几台 | 这组机器在第 3 时段开着不超过 3 台，还是至少 4 台？ |

“开着几个时段”和“启动几次”不同：连续开 4 个时段，可能只启动过 1 次。
“组”则是按机组属性事先划分的集合，不是 LLM 临时随意拼出的机器名单。

### 5.2 为什么这类拆分不会漏掉合法计划？

假设简化题算出 A 在 4 个时段内的开机计数是 2.4。
真实计划中，这个计数一定是 0、1、2、3 或 4，不可能是 2.4。

我们就拆成：

- 不超过 2 个时段：包含 0、1、2。
- 至少 3 个时段：包含 3、4。

每个真实计数都在某一边，既没有遗漏，也没有重叠。
这解释了拆分为什么合理，但还不能保证拆分后更容易算。

而且程序必须保证两条限制分别只加在各自的子问题里。
如果错误地把两条都加到父问题上，就会变成“既不超过 2 又至少 3”，破坏问题。
这正是编译和测试的重要性。

### 5.3 DSL 和编译器不需要想得太神秘

DSL 在这里就是一张“允许提哪些问题”的受限菜单。
我们不允许生成的程序随意改供电要求、删成本或直接操作所有求解器内部状态。

“编译器”则把菜单上的一句话翻译成 SCIP 真正执行的两个子问题。
它既要翻译正确，也要尽量便宜。我们现在的麻烦，部分就在这个翻译层。

## 6. 到目前为止，哪些事情已经完成？

| 阶段 | 白话目标 | 已做到 | 还不能因此声称 |
|---|---|---|---|
| Phase -1 | 先确认借来的工具能用 | 官方问题、短搜索、保存恢复、程序导出和参数优化链路跑通 | 复现了真实 LLM 的搜索质量或论文全部成绩 |
| Phase 0 | 把题目换成发电机安排 | UC 模型、四种变量规则、独立检查和搜索接口跑通 | 我们的规则比默认 SCIP 快 |
| Phase 1 | 让求解器能问新问题 | 四类分支、检查、子问题创建、出错回退可运行 | 新问题比旧问题更有价值 |
| Phase 2 | 实际比赛，看新问题有没有帮助 | 完成 30 个实例、7 种方法、210 次短预算评估 | 已完成充分预算验证或通过收益门槛 |

有三条边界特别重要：

- 前面的搜索测试使用了 mock：它像一位只会提交预设程序的临时代班者。求解器是真的，但不能据此说真实 LLM 已经学会设计好规则。
- Phase 2 完全没有调用 LLM，规则由我们事先写好。这是先验证研究想法，而不是先训练模型。
- 测试通过说明检查覆盖到的情况没有失败，不是对所有未来问题的万能保证。

## 7. 这次实验究竟得到了什么结果？

实验题目是 30 个不同的 UC 实例，覆盖 10、20、50 台机组和 5 类场景。
每个实例只有 8 个时段，每种方法每次最多给 SCIP 3 秒，并且只跑了一次。

“题目”也会被叫作 instance；“seed”是生成题目时用于重现随机选择的编号，
不是模型训练轮数，也不是某种机组类型。

| 方法 | 白话解释 | 30 个实例中证明最优的数量 |
|---|---|---:|
| native_default | 原样使用 SCIP | 21 |
| matched_default | 使用为新方法改造的模型，但仍由 SCIP 默认策略选择分支 | 14 |
| pseudocost | 依据以往分支效果估计，选择一个变量 | 13 |
| llm4branch | 使用 Phase 0 的固定变量评分程序，不是本轮新搜索出的程序 | 11 |
| start | 优先问启动次数，不适合时退回变量规则 | 13 |
| temporal | 优先问开机时段计数，不适合时退回变量规则 | 13 |
| hybrid | 按固定顺序尝试几种结构问题，不适合时退回变量规则 | 12 |

全部 210 次都找到了通过检查的合法发电计划，但不都证明了最优。
本轮还实际执行了 585 次结构分支：不是因为新规则根本没被调用，才没有看到总体优势。

### 怎么读这些数字？

- 原生 SCIP 的“证明最优”数量最多，这是已观察到的事实。
- 结构规则有时比某个变量评分程序好，但没有形成稳定的总体优势。
- 不能从这张表推导出“结构分支永远没用”，因为题目和时间预算都有限。

还有一点：有些改造后的方法更早找到了第一个计划，在“整个过程中答案与证明相差多远”的指标上更好。
所以不是所有指标都一边倒。我们不能只挑对自己有利的一项成绩。

## 8. 当前困境是什么？分清事实与猜测

### 困境一：为了装上新功能，暂时牺牲了原软件的一部分能力

SCIP 在正式搜索前会做“预处理”：提前化简题目、消掉不必要的变量、推断某些条件。
可以理解为解题前先整理线索，减少后面的工作量。

目前锁定的软件接口，不方便直接实现我们想要的某些局部计数限制。
我采用的兼容办法是：额外增加表示计数的变量，并关闭预处理，以免它们被合并后无法设置子问题限制。

这是一条先把正确性验证跑通的路，不是已经优化好的性能方案。
不能理解为“SCIP 理论上做不了”，问题在于当前版本、接口和我们所选的实现方式。

**事实：** 即使不用人工规则，同样的模型改造也让默认策略从 21 个解至最优降到 14 个。

**合理怀疑：** 额外模型规模和失去预处理能力，是重要负担。

**还不知道：** 两种改变各自占多少，以及换一个更合适的实现后能恢复多少性能。
增加等价的计数等式本身，不等于把原数学问题变成了另一个更差的问题。

### 困境二：我们的新问法还没有选得足够聪明

当前规则主要看“计数离整数远不远”，再按照固定优先级选问题。

例如计数是 2.5，确实看起来“不确定”；但对它拆分，可能没有排除多少有用可能性。
另一个看起来不那么不确定的开关，反而可能牵动后面多个时段。

**事实：** 在同样改造后的模型上，人工规则也没有稳定超过默认 SCIP。

**合理怀疑：** 我们用来选择结构问题的信号过于简单，尚未抓住真正有帮助的状态。

**还不知道：** 哪一类机器、时间窗口、供需状态最适合这种问法。
还需要观察“问完以后发生了什么”，而不是只观察“问之前看起来多不确定”。

### 困境三：不问新问题时，退回的规则也变了

当前人工规则不触发时，回到 pseudocost，而不是完全回到 SCIP 默认策略。
默认 SCIP 可能利用比这个单一估计更丰富的机制。

因此，人工方法和默认方法之间的差距，可能同时来自“新问题选得怎样”和“后备规则怎样”。
这两个影响需要分别测试，不能都归结为结构分支本身。

### 困境四：考场太短，还不足以下最终判决

3 秒是一轮很短的测试。尤其对 50 台机组，有些时间主要花在最初的数学计算上，
新分支规则还没来得及充分发挥。

而且我们只有简化题目、每例单次运行、共享计算环境。
这些结果足以发现明显工程负担，不足以证明在真实、长时间调度任务中的最终表现。

### 为什么不能只看“节点更少”？

可以把节点看成要处理的子题目数。新方法即使减少了题目数，
也可能让每道题更难，或者光选题就花很久。

反过来，超时前只处理了一个节点，也不一定是好事：它可能一直卡在第一道题。
所以必须一起看用时、完成数量、答案质量，而不是只看节点数。

## 9. 怎么一步一步弄清楚，而不是凭感觉改代码？

先问可检验的问题，再决定改什么。下面是建议的下一轮实验，不是已经完成的工作。

### 第一步：到底是哪项改造拖慢了求解？

在同一批题目上，先让 SCIP 继续使用自己的默认规则，分别测试：

1. 原模型，正常预处理。
2. 原模型，关闭预处理。
3. 增加计数变量，关闭预处理。

第 1 与第 2 的差别，帮助看关闭预处理的代价。
第 2 与第 3 的差别，帮助看额外计数表示的代价。
这些效果可能互相影响，不应机械地把差值当成普遍规律。

如果第 2 步已经明显变慢，应优先恢复正常预处理，而不是马上调人工规则的几个数字。
下一项工程任务是验证另一种把计数问题交给 SCIP 的方式，尽量不关闭它原有的能力。

### 第二步：某个结构问题本身到底有没有帮助？

从少量固定的求解状态出发，分别试：

- 原本准备问的单个开关。
- 一个开机计数问题。
- 一个启动计数问题。

看看哪种拆法更快排除一边，或者更快缩小答案的不确定范围，同时计入尝试的成本。
这个实验必须从可比较的状态出发，不能拿两棵不同搜索树上的随意节点硬比。

如果在局部也没有帮助，应先调整问法和候选范围。
如果局部确有帮助、完整求解却变慢，才进一步调查调用时机、频率和实现开销。
局部成绩好仍不保证整体成绩好。

### 第三步：保留默认后备规则，只在有把握时问新问题

不要强迫每一步都使用新功能。先试只在树的最前面、少数合适状态触发，
其余时候交还默认策略；再与 pseudocost 后备方案对照。

这相当于先证明“偶尔多问一个好问题”有用，再考虑扩大使用范围。

### 第四步：延长考试时间，重复考试

在上述问题有初步答案后，再增加时限、时段数量和重复次数。
提前固定比较方式，不因某个结果不好就临时换题或删掉超时记录。

开发时用过的题目也不能一直充当最后的考试题。以后需要保留没有用于选规则的新题目。

### 你参与讨论时，可以反复问我这五个问题

1. 这次只改变了什么？是否同时改变了别的东西？
2. 与谁比较，为什么这个对照公平？
3. 比的是找到一个计划，还是证明它最好？
4. 这个结论是实际测出来的，还是我们的猜测？
5. 如果结果相反，下一步会怎么做？

你不必先记住大量术语，也可以用这些问题监督实验是否合理。

## 10. 为什么现在不直接训练 LLM？

后面的路线确实包含 SFT 和 DPO，但它们不是修复当前问题的万能按钮。

- SFT 可以先理解为：给模型展示一批经过验证的好程序，让它学习写法和规律。
- DPO 可以先理解为：给模型展示同一任务下哪个程序更好，让它学习偏好。

正式训练会改变模型内部权重，不只是把几个例子放进一次聊天。

前提是我们知道什么样的程序真的好，并且评价相对可靠。
如果现阶段的评分主要受接口代价、超短时限或不公平对照影响，
训练可能让模型更擅长迎合这些问题，而不是写出真正有用的规则。

所以应先把“判断好坏的尺子”和“执行规则的底座”弄可靠。
这并不说明必须先有完美人工算法才能用 LLM，而是说明目前没有理由把问题都归因于模型不够聪明。

## 11. “阶段完成”和“门槛通过”分别意味着什么？

Phase 是工作阶段。Gate 是继续往后投入之前要跨过的证据门槛。

现在可以说：

> Phase 2 的这轮短预算实验执行完了，结果和代码有记录。

现在不能说：

> 已经证明结构化分支有效，可以直接开始后训练。

还有一个需要透明说明的地方：技术路线要求至少在一类问题或搜索状态上看到明确收益。
我在这轮实验中采用了更严格的具体判定：按每个场景的 6 个实例汇总，要求相对四个对照
都降低至少 10% 的总时间和总节点数，并满足其他条件。

这些具体数字是本轮采用的实验标准，不是路线原文规定，也不是行业统一标准。
它未通过，不代表已经排除了所有有价值的局部发现。
但在找到更可靠证据之前，也不能随意降低门槛，只为了把结果写成成功。

## 12. 常见误解与术语速查

### 几个直接回答

**这个项目是不是让聊天机器人直接控制发电机？**

不是。我们研究的是计算方法；当前没有真实电网控制部署。

**是不是 LLM 越大，求解就一定越快？**

不是。最终取决于它提出的小程序是否有效、执行是否便宜，以及评价是否公平。

**现在没赢，是不是研究方向已经错了？**

证据还不足以下这个结论。现有实现、人工规则和实验预算都还存在明显限制。
但也不能因为方向听起来合理，就假定以后一定会赢。

**如果所有方法都得到一样的最低发电成本，我们还有什么研究价值？**

能够更快证明同一个最优答案，本身就有价值；时间不足时，也可以比较找到计划的速度和质量。

**为什么不用论文里公布的成绩直接证明我们有效？**

题目、规则、模型和环境都变了。上游公布的结果不能代替我们的 UC 实验，
我们目前也没有独立复现其全部性能结论。

### 遇到这些词时，可以这样理解

| 术语 | 在本项目中先这样理解 |
|---|---|
| MILP | 同时含开关类选择和连续数值、并以线性关系描述的一类数学题 |
| B&B / 分支定界 | 把大问题拆开，利用可证明的界排除不值得继续的部分 |
| 特征 | 用数字描述一个候选或当前状态 |
| 基线 / baseline | 用来公平比较的已有方法 |
| 启发式 / heuristic | 可能有帮助的经验规则，不保证每次更快 |
| 回退 / fallback | 新规则不能用或不适合时，交给后备方法 |
| 编译后端 | 把我们提出的分支问题变成求解器操作的实现部分 |
| 消融实验 | 有控制地去掉或加入一项改变，调查它的影响 |
| PDI | 随时间累计“当前最好计划与已知成本下限的差距”；这里记录的是采样近似值 |
| Test / OOD | 未用于挑规则的测试题 / 与开发题分布不同的题目 |
| 冻结规则 | 选定并固定程序和参数，正式使用时不继续改规则或调用 LLM |
