# 项目全景：你需要掌握的架构、选择权和大规模路线

更新：2026-09-18。本文描述现有代码，不把未来计划画成已完成的功能。
基础概念见 [新手文档](BEGINNER_GUIDE_ZH.md)。

## 1. 首先改变研究顺序

你的经验是：小题上成立的规律，到了大题上未必成立。
本项目应从一开始就在目标规模上检查想法，而不是等小题调好了才放大。

- 小规模保留，但只负责检查代码和数学关系有没有写错。
- 目标规模负责判断规则是否真的有用；开发时就应使用这一规模。
- 最后另留没用于挑规则的同规模题目，以及更大或不同场景的题目，防止只会做练习题。

原来 10/20/50 台、8 时段、3 秒的结果只保留为历史初步实验，不替目标规模作结论。
你已说明：以前从 50 台开始，后来提高到 200、500 台；历史时段数是 8 还是 24 暂不确定。
据此把 200、500 台作为主要开发规模，50 台只作检查和对照，100 台可作工程过渡检查。
24 时段作为当前起步假设、48 时段作为后续扩展；时段长度及真实数据来源仍待确认。

## 2. 完整系统有两条路线，不是一条已经全部接通的管道

### 路线 A：实际算一道 UC 题（已实现）

```text
机组参数、各时段用电需求
        │
        ▼
UC 建模：把“合法且省钱的安排”写成数学条件
        │
        ▼
SCIP 求解器：计算、排除方案、维护答案与证明
        │  遇到需要拆题的时刻
        ├── 默认策略：由 SCIP 自己决定
        ├── 变量策略：给单个开关打分，选一个拆题
        └── 人工结构策略：选择开机计数/启动计数/组计数
                         │
                         ▼
                  翻译成两个子问题
                         │
                         └── 回到 SCIP 继续求解
        │
        ▼
结果：发电计划、成本、时间、是否证明最优
        │
        ▼
独立校验与实验记录
```

三个策略分支是可选择的方法，不是每次求解都依次经过它们。
人工结构策略内部还有后备规则：当前 Phase 2 用 pseudocost；Phase 1 则交回 SCIP 后续规则。
这是两个实验入口的真实差异，不能笼统说“它们都退回默认策略”。

### 路线 B：提前设计更好的规则（部分接通）

```text
任务说明 + 已有规则与成绩
        ↓
LLM 提议小程序
        ↓
检查程序 → 调整小程序中的数字 → 用路线 A 实际考试
        ↓
OpenEvolve 保存程序、成绩和修改关系
        ↓
继续提出新程序，最后选择并固定一条规则
```

已有：变量评分程序的这条链路通过 mock 响应跑通。
未完成：真实 LLM 的有效搜索验证、让这条搜索链路生成我们的结构化 DSL 程序。
目前结构规则是人写的，并没有接到完整的自动结构搜索流程。

未来的 SFT/DPO 是让 LLM 从可靠的好坏程序记录里学习，目前没有训练。
最终部署只运行固定小程序，不让大模型在每一个搜索节点上临时作决定。

## 3. 每一层由谁负责、能改什么？

| 层 | 白话职责 | 当前文件/组件 | 改动会影响什么 |
|---|---|---|---|
| 题目 | 决定考哪种电力安排问题 | `src/ucbranch/uc.py::generate` | 规模、难度、规律是否真实 |
| 数学模型 | 写出必须满足的条件和费用 | `uc.py::build` | 原问题本身；不能为了变快随意删条件 |
| 求解器 | 真正计算、搜索和证明 | 锁定 SCIP | 性能和数值行为；升级必须重新核验 |
| 状态信息 | 把求解状态转成可用数字 | 定制 Ecole、`integration.py` | 规则看得到什么、读取有多贵 |
| 候选菜单 | 枚举允许选择的结构问题 | `structured.py::specifications` | 选择空间及每次扫描的成本 |
| 选择规则 | 决定此刻选哪个问题 | `solver.py`、`phase2.py` | 搜索走向；不能据此修改 UC 限制 |
| 分支翻译 | 将选中的问题变成两个子问题 | `structured.py::StructuredBranchrule` | 正确性、模型大小、求解器设置 |
| 评价 | 检查计划，记录成绩，公平比较 | `validate`、`evaluator.py`、`scripts/phase2.py` | 哪种程序会被判成“好” |
| 自动搜索 | 管理提出、评估、保留程序 | 上游 OpenEvolve | 试多少程序、如何保留与恢复 |
| 后训练 | 利用好坏程序改善 LLM | 尚未实现 | 是未来工作，不是现在的阻塞原因 |

两条最重要的边界：

1. 规则负责“怎样找”，UC 模型负责“什么答案合法”。不能让规则偷偷改变合法答案集合。
2. 同一组性能比较必须用相同题目和预算；改变了模型表示或预处理，要单独列为一个实验因素。

## 4. 当前不是一个统一实验入口：这也是需要透明说明的地方

| 入口 | 用途 | 重要限制 |
|---|---|---|
| `scripts/phase0.py` | 变量分支基线与 OpenEvolve 接入 | 搜索验证使用 mock；不是结构程序搜索 |
| `scripts/phase1.py` | 检查四类结构分支真的正确执行 | 正确性检查，不是公平性能结论 |
| `scripts/phase2.py` | 旧的 30 实例人工规则试跑 | 固定小规模协议和特殊 Gate 判定，不可直接用于大规模结论 |
| `scripts/scale_probe.py` | 新增规模与原生 SCIP 能力检查 | 不测试结构收益，不训练、不调用 LLM |

保留旧入口，是为了不偷偷改写历史实验定义。新规模检查不覆盖旧结果。
未来应在确定目标数据后统一正式实验入口，而不是不断增加互不兼容的临时脚本。

## 5. 我之前做了什么临时选择？现在有什么风险？

### 选择一：加“计数记录栏”，并关闭解题前的化简

当前每个计数问题对应一个额外连续变量和一条等式，类似提前给所有问题建记录栏。
为了避免这些记录栏被预处理合并后无法设置子节点界，我关闭了预处理。

好处：分支可以正确运行。代价：改变了原生 SCIP 擅长处理问题的方式。
它不是必须永远采用的架构，更不能因为已写好就一直围着它调规则。

### 选择二：枚举很多窗口，再逐个看

每台机组都枚举长度 2、4 的窗口，分别考虑开机计数与启动计数。
每次浅层决策都会扫描候选；交给策略前还会复制候选数据。
这在小题上可能不明显，在大题上可能成为主要负担，尚未做详细耗时剖析。

以 500 台、48 时段为例，在当前模型中：

- 原始开关位置：24,000 个。
- 原始变量约 96,000 个（开关、出力、启动、停机）。
- 两类单机窗口计数会额外产生 92,000 个记录变量及等式。
- 六个机组组别还会产生 288 个记录变量及等式。

这只是按代码数出的结构规模，不是内存和运行时间预测。
它说明不能简单把机组数调大后，原封不动地跑旧的全候选方案。

### 选择三：用非常短的考试判断完成数量

3 秒对大题往往不足以进入有代表性的搜索阶段。
大规模也不能一律要求全部证明最优才比较：可能需要比较固定时间内计划质量、剩余不确定范围、首次可行计划时间。
这些标准要先确定，不能看完结果再挑对我们最有利的指标。

### 选择四：生成器方便，但还不代表真实大规模数据

增加机器数量不会自动增加真实复杂性。当前机组参数范围较窄、最小开停机时间相同，
需求由短周期正弦变化与小扰动生成，初始状态全部关闭。
把时段拉长，只会继续这一设定，不自动变成真实的一天或两天负荷曲线。

因此优先考虑沿用你已有工作的实例；接入时明确时间单位、成本单位、初始开关状态、
初始出力、已连续开停多久等信息。现在还没有完成外部数据集导入器。
拉格朗日松弛与本项目的求解路径也不同，旧经验帮助我们选题，但不直接证明新方法有效。

## 6. 现在怎样扩大规模，同时不把问题搅在一起？

### A. 先确认“题目是什么”

目标机组数按你的历史工作采用 200、500 台。
时段数先按 24 起步，48 作为后续扩展；仍需明确时段长度与数据来源。
100 台只用来检查工程入口，不能取代 200、500 台上的规则开发和验证。

### B. 先让未经结构改造的 SCIP 做目标规模题目

记录建模时间、原始变量/约束数量、求解时间、是否找到合法计划、剩余 gap、节点数。
这样才能知道卡在“题目建得慢”“根节点计算慢”还是“后面的搜索很多”。
新脚本默认只打印计划，不启动批量求解：

```bash
.conda/llm4branch/bin/python scripts/scale_probe.py
```

明确指定一个工程检查任务后才执行，例如：

```bash
.conda/llm4branch/bin/python scripts/scale_probe.py \
  --units 100 --horizons 24 --seeds 100 --limit 10 \
  --output outputs/scale-n100-h24-check --run
```

10 秒只检查运行与记录是否可用，不作性能判断。
默认计划是 6 次、每次求解最多 30 秒；这不包括建模、写文件等时间，
也不是对整个进程的硬超时或内存限制。启动更大批次前还要评估机器资源。

### C. 在目标规模上分开验证工程代价和规则价值

固定同一批实例，依次比较：原生默认、仅关闭预处理、再添加计数表示、最后加入结构规则。
这些消融对照尚未全部实现，不要把新增的规模检查误读成它们已完成。

不能等小题规则调得很好才做这一步。每一项改动从早期就要查看目标规模上的表现。

### D. 让评价方式适合大题

对难以完全解完的题，保留各个固定时间点的最好计划、成本下限与 gap。
各方法使用相同实例、预算和资源；报告未找到可行解的情况，不删除失败题目。
开发规模与最终测试规模一致，但具体实例必须分开，避免反复挑规则后又用同一批题证明自己。

## 7. 怎样防止我继续钻进一个实现方案里？

以后每次实质性改动前，我应先给你一张简短“决策卡”：

| 项目 | 必须说清楚 |
|---|---|
| 这次问题 | 例如：关闭预处理是不是主要损失来源？ |
| 改动层 | 数据、模型、候选、规则、翻译器，还是评价？ |
| 不动什么 | 同一批题、时间预算和其他设置保持不变 |
| 两条可选路 | 至少解释一个替代方案，不能把当前代码当成唯一可能 |
| 目标规模 | 在你关心的规模上测，不只展示小题 |
| 成功证据 | 预先说用什么结果支持判断 |
| 停止条件 | 没有证据就停止这条路，而不是无限追加调参 |
| 结果性质 | 工程检查、原因诊断，还是研究收益验证？ |

你负责确认研究目标和可接受的取舍，不需要先学会所有 SCIP 接口。
我负责把选择、代价和不确定性解释清楚，不能把理解全部底层代码的负担转给你。

改变正式目标规模、数据假设、成功标准，或启动显著更昂贵的完整实验之前，应先与你明确讨论。
这些讨论不是要求你替我排查技术细节，而是确保我没有偏离你的研究问题。

## 8. 读代码时的最短路线

1. `uc.py`：我们到底在解什么题。
2. `structured.py`：可以问什么新问题，以及问题怎样交给 SCIP。
3. `phase2.py`：哪条规则在什么情况下使用、怎样记成绩。
4. `scripts/phase2.py`：旧实验考哪些题、如何汇总。
5. `evaluator.py` 与 `scripts/phase0.py`：以后怎样把一次求解接回自动程序搜索。

先理解这五块的边界，比先阅读整套上游框架更有帮助。
本文描述的是当前真实系统；新后端、正式大规模对照、结构程序自动搜索和模型训练仍是待完成工作。
